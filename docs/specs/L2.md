# L2 - Detailed Requirements

## L2-001: Editor Sign-In and Session Persistence
**Traces to:** L1-001

The system must authenticate registered co-op board editors on `/sign-in` using their e-mail address and password, support toggling password visibility, persist the session for 30 days when "Keep me signed in on this device" is checked, and allow signed-in editors to view their identity or sign out from the account menu dialog.

**Acceptance Criteria:**
1. Given an unauthenticated editor on `/sign-in`, when the editor enters a valid registered e-mail address (`margaret@harbourviewcoop.ca`) and valid password with "Keep me signed in on this device" checked and submits the form, then the submit button displays `[aria-busy="true"]` during submission, the system creates a 30-day authenticated session, and redirects the editor to `/`.
2. Given an unauthenticated editor on `/sign-in`, when the editor clicks the "Show password" button (`aria-label="Show password"`), then the password input type toggles from `password` to `text` and `aria-pressed` changes from `"false"` to `"true"`.
3. Given an unauthenticated editor on `/sign-in`, when the editor submits an unrecognized e-mail address or incorrect password, then the system returns HTTP `401 Unauthorized` and displays a danger alert (`role="alert"`) stating that the e-mail address or password was not recognized while preserving the entered e-mail address.
4. Given an editor whose session has expired, when the editor is redirected to `/sign-in?expired=1`, then the sign-in screen displays an informational banner or alert notifying the editor to sign in again to continue.
5. Given a signed-in editor on any studio page, when the editor activates the topbar avatar button (`aria-label="Account menu for Margaret Chen"`), then the account menu dialog opens displaying the editor's full name, e-mail address, board role, links to "Site & account settings" and "Headless API explorer", and a "Sign out" action that terminates the session and redirects to `/sign-in`.
6. Given any viewport from extra small (`<576px`) through extra large (`>=1200px`), when the editor views `/sign-in`, then `.auth-card` remains centered within `.auth-layout` at `width: 100%` up to `max-width: 26rem` without horizontal scrolling.

## L2-002: Sign-In Form Validation and Error Summary
**Traces to:** L1-001

The system must validate the `/sign-in` form fields prior to submission and display both an accessible form-level error summary and field-level error messages when inputs are missing or malformed.

**Acceptance Criteria:**
1. Given an editor on `/sign-in`, when the editor submits the form with an invalid e-mail address (`margaret@`) and an empty password, then the system prevents submission, renders `.form-summary` (`role="alert"`, `tabindex="-1"`) titled "Fix 2 things to sign in" with anchor links to `#email` ("Enter an e-mail address like name@harbourviewcoop.ca") and `#password` ("Enter your password"), and moves keyboard focus to `.form-summary`.
2. Given an invalid `/sign-in` submission, when field errors are displayed, then `#email` and `#password` each have `aria-invalid="true"` and `aria-describedby` pointing to their respective `.field__error` element, and the user's entered e-mail value is preserved.

## L2-003: Password Reset Link Request
**Traces to:** L1-001

The system must allow an editor on `/forgot-password` to request a single-use password reset link valid for 1 hour by submitting their e-mail address.

**Acceptance Criteria:**
1. Given an unauthenticated user on `/forgot-password`, when the user enters a valid e-mail address (`margaret@harbourviewcoop.ca`) and activates "Send reset link", then the system generates a single-use reset token expiring in 60 minutes, dispatches the reset e-mail, and transitions to the confirmation state without disclosing whether the e-mail address is registered.
2. Given an unauthenticated user on `/forgot-password`, when the user submits an empty or malformed e-mail address, then the system renders `.form-summary` (`role="alert"`) and marks `#email` with `aria-invalid="true"` and an inline `.field__error` message.
3. Given an unauthenticated user on `/forgot-password`, when the server fails to process the request, then the system displays a danger alert (`role="alert"`) allowing the user to retry while preserving the entered e-mail address.
4. Given any viewport from extra small (`<576px`) through extra large (`>=1200px`), when the user views `/forgot-password`, then the card and full-width submit button (`btn--block`) adapt cleanly to the viewport width.

## L2-004: Password Reset Completion with Token
**Traces to:** L1-001

The system must allow an editor opening `/reset-password` with a valid, unexpired single-use reset token to set a new password of at least 10 characters.

**Acceptance Criteria:**
1. Given an editor on `/reset-password` with a valid reset token, when the editor enters a "New password" (`#new-pw`) of at least 10 characters and a matching confirmation in "Type it again" (`#confirm-pw`) and submits "Save new password", then the system updates the editor's password hash, invalidates the reset token immediately, and displays the success state with a link to sign in.
2. Given an editor on `/reset-password`, when the editor submits a password shorter than 10 characters or a confirmation that does not match `#new-pw`, then the system prevents submission, focuses `.form-summary` (`role="alert"`), and marks the offending input(s) with `aria-invalid="true"` and descriptive `.field__error` messages.
3. Given an editor opening `/reset-password` with an expired or already-used token, when the form is submitted or loaded, then the system returns an error state with a danger alert and a link to `/forgot-password` to request a fresh link.

**Traces to:** L1-002

The system must allow an invited board member opening `/accept-invite` with a valid 7-day invitation token to review their pre-verified e-mail and board role, enter their full name, choose a password of at least 10 characters, and join Esplanade.

**Acceptance Criteria:**

## L2-010: Composing and Reordering Typed Page Sections
**Traces to:** L1-004

The system must allow editors on `/pages/:id` (`page-editor`) to compose a page from ordered, strongly typed section blocks (`Hero`, `Text Block`, `Image Gallery`, `Callout`, `FAQ List`), add new sections via the `add-section` dialog, reorder sections using keyboard-accessible "Move up" and "Move down" buttons, and save changes as a draft.

**Acceptance Criteria:**
1. Given a signed-in editor on `/pages/:id`, when the page editor loads, then each section renders inside a `.block-card` showing its 1-based position and section type badge (`Section 1 · Hero`, `Section 2 · Text Block`, `Section 3 · Callout`, `Section 4 · FAQ List`), type-specific form fields, and reorder controls.
2. Given a page with multiple sections on `/pages/:id`, when the first section is rendered, then it displays "Move down" and omits "Move up"; when an interior section is rendered, then it displays both "Move up" and "Move down"; when the last section is rendered, then it displays "Move up" and omits "Move down".
3. Given a page with multiple sections on `/pages/:id`, when the editor activates "Move up" or "Move down" on a section, then the section swaps positions with its adjacent neighbor and section numbers update sequentially.
4. Given an editor on `/pages/:id`, when the editor activates "Add section", then the `add-section` dialog opens allowing the editor to choose a "Section kind" (`Text Block`, `Image Gallery`, `Callout Box`, `FAQ List`) and enter a required "Section heading" (`#sec-heading`).
5. Given the `add-section` dialog is open, when the editor submits with an empty `#sec-heading`, then the dialog transitions to `invalid` and marks `#sec-heading` with `aria-invalid="true"` and an inline `.field__error`; when submitted with a valid heading and kind, then the new section block is appended to the page.
6. Given an editor on `/pages/:id`, when the editor activates "Save draft", then the page changes are persisted with status `Draft changes` (`draft_changes`), the submit button shows `[aria-busy="true"]` while saving, and a success notification confirms the draft was saved.

## L2-013: Deleting a Site Page and Root Page Protection
**Traces to:** L1-004

The system must prevent deletion of the root home page (`/`) and require confirmation via the destructive `delete-item` dialog before removing any other page.

**Acceptance Criteria:**
1. Given a signed-in editor on `/pages`, when the row for `Home` (`path: "/"`) is rendered, then no delete button is rendered for that row, and any `DELETE` request against the root page `/` must be rejected by the API with HTTP `400 Bad Request` or `409 Conflict`.
2. Given a signed-in editor on `/pages`, when the editor activates the delete button (`aria-label="Delete Living at Harbourview"`) on a non-root page, then the `delete-item` dialog opens (`role="dialog"`, `aria-modal="true"`) naming the page title, URL path, and section count to be removed from the next published snapshot and warning that its header menu link will be unlinked.
3. Given the `delete-item` dialog opens, when initial focus is placed, then focus lands on the safe cancel action ("Keep page" with `autofocus`) rather than the destructive `.btn--danger` ("Remove page") button.
4. Given the `delete-item` dialog is open, when the editor activates "Remove page", then the page is removed, its menu link is unlinked, and the deletion is staged for the next published snapshot.

## L2-036: Input Sanitization, Secret Hashing, and Rate Limiting
**Traces to:** L1-013

**Acceptance Criteria:**
1. 2. Given user-supplied strings in page sections, articles, events, member profiles, or public inquiries containing HTML/script injection payloads (e.g., `<script>alert(1)</script>`), when stored or rendered in the Angular client or JSON API, then the system encodes or sanitizes the content so no arbitrary JavaScript executes (XSS prevention) and uses parameterized queries for all data access (SQL injection prevention).
3. Given repeated failed requests to `/sign-in`, `/forgot-password`, or `POST /v1/inquiries` from the same client exceeding the configured threshold within 1 minute, when an additional request arrives, then the API returns HTTP `429 Too Many Requests`.
